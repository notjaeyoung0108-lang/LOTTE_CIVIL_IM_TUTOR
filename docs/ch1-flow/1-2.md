# 1-2. 공정관리 기본 Flow

## 이 Flow가 답하는 질문

> **그 일이 언제 되는가. 그리고 계획대로 되지 않았을 때 무엇을 하는가.**

1-1의 시공 Flow가 "물건이 만들어지는 순서"였다면, 공정관리 Flow는 그것을 **시간이라는 자로 재는 일**이다. 대상은 같고 보는 각도가 다르다.

---

## 전체 그림

```text
 ①공사범위 → ②WBS → ③Activity → ④선후관계 → ⑤Duration → ⑥Resource·Constraint → ⑦Baseline
 └─────────────────────── 계 획 (무엇이 언제 되는지 정한다) ───────────────────────┘

 → ⑧실행 → ⑨실적수집 → ⑩계획 대비 비교 → ⑪지연 영향 분석 → ⑫Recovery → ⑬Update
   └────────────── 통 제 (실제와 계획의 차이를 다룬다) ──────────────┘
                                                                    │
                    └───────────────────────────────────────────────┘
                              고친 계획으로 다시 ⑧ 실행
```

앞의 일곱 칸은 **계획**이고 뒤의 여섯 칸은 **통제**다. 그 경계에 ⑦ Baseline이 있다.

그리고 이 Flow는 끝나지 않는다. ⑬에서 계획을 고치면 다시 ⑧로 돌아가 공사가 끝날 때까지 돈다. **공정관리는 한 번 하는 일이 아니라 계속 도는 고리다.**

---

## 왜 이 순서인가

계획 구간의 일곱 칸은 **각 칸이 앞 칸의 답을 입력으로 받는다.** 순서를 바꿀 수 없는 이유가 여기 있다.

```text
범위가 정해져야     →  무엇을 나눌지 알 수 있고 (WBS)
나뉘어야           →  무슨 작업인지 정의할 수 있고 (Activity)
작업이 정의돼야     →  어느 것이 먼저인지 정할 수 있고 (선후관계)
순서가 정해져야     →  각각 며칠인지 따질 의미가 있고 (Duration)
기간이 나와야      →  언제 누가 무엇이 필요한지 알 수 있고 (Resource)
그게 다 모여야     →  비교할 기준을 얼릴 수 있다 (Baseline)
```

초보자가 흔히 하는 실수는 ②③④를 건너뛰고 바로 날짜를 잡는 것이다. 그러면 "왜 그 날짜인가"에 답할 수 없고, 하루가 밀렸을 때 **무엇에 영향을 주는지도 알 수 없다.**

---

## ① 공사범위 파악

내가 계획해야 할 대상이 어디부터 어디까지인지 정한다.

당연해 보이지만 실제로는 경계가 모호한 경우가 많다. 다른 업체가 하는 부분, 발주처가 직접 하는 부분, 계약에 포함되지 않은 부분이 섞여 있다. 범위를 고정하지 않으면 뒤의 모든 칸이 흔들린다.

**Input** 계약 내역, 설계도서, 시공계획
**Output** 계획 대상 범위와 제외 범위의 기술

---

## ② WBS

### WBS란 무엇인가

**WBS(Work Breakdown Structure, 작업분류체계)** 는 공사 범위를 관리할 수 있는 크기의 단위로 쪼갠 체계다.

여기서 중요한 구분이 하나 있다. **WBS는 "무엇을 만들어야 하는가"를 나눈다. "언제 어떤 순서로 하는가"는 나누지 않는다.**

초보자는 WBS를 만들 때 자기도 모르게 순서를 집어넣는다. "1. 터파기 2. 버림 3. 저판"은 WBS가 아니라 순서다. WBS는 "저판이라는 결과물"까지만 말하고, 그것을 언제 하는지는 ④에서 정한다.

### 왜 쪼개는가

목적은 세 가지다. 그리고 **이 세 가지가 쪼개는 크기를 정하는 기준이기도 하다.**

| 목적 | 쪼개지 않으면 |
|---|---|
| **진도 측정** | "공사 60%"밖에 말할 수 없다. 어디가 끝났는지 모른다 |
| **책임 지정** | 누가 무엇을 끝내야 하는지 지정할 대상이 없다 |
| **근거 추적** | 도면이 바뀌었을 때 어느 범위가 영향받는지 되짚을 수 없다 |

**너무 크게 나누면** 진도를 말할 수 없고 담당을 지정할 수 없다. **너무 잘게 나누면** 관리에 드는 시간이 관리로 얻는 이익보다 커진다. 진도를 따로 재지 않을 것이라면 나눌 이유가 없고, 담당자를 따로 지정할 수 없다면 나눠도 관리되지 않는다.

### 어떻게 나누는가

일반적으로 세 가지 기준을 겹쳐서 쓴다.

- **위치** — 어디인가 (구간, 층, 블록)
- **공종** — 무슨 일인가 (토공, 철근, 콘크리트)
- **관리 결과물** — 무엇을 완료해서 넘기는가

```text
지하차도 구조물
├─ 구간 A
│  ├─ 저판
│  ├─ 벽체
│  └─ 상부슬래브
└─ 구간 B
   ├─ 저판
   ├─ 벽체
   └─ 상부슬래브
```

**Output** WBS 코드 체계, 각 코드의 포함·제외 범위를 적은 WBS 사전

---

## ③ Activity

### WBS와 무엇이 다른가

**Activity(액티비티, 작업)** 는 기간을 가지고 실제로 수행되는 일의 단위다.

```text
WBS        "구간 A의 벽체"          ← 결과물. 명사.
Activity   "구간 A 벽체 철근 배근"    ← 작업. 동사가 붙는다. 기간이 있다.
```

하나의 WBS 아래에 여러 Activity가 붙는다. 벽체라는 결과물 하나를 만들기 위해 철근·거푸집·타설·양생이라는 여러 작업이 필요하다.

### Activity가 되려면

- **시작조건이 명확할 것** — 무엇이 갖춰지면 시작할 수 있는가
- **완료조건이 명확할 것** — 무엇이 되면 끝난 것인가
- **책임자를 지정할 수 있을 것**
- **진도를 잴 수 있을 것**

특히 **완료조건**이 중요하다. "철근 배근"의 완료가 배근을 끝낸 시점인지, 자체점검까지인지, 검측 통과까지인지에 따라 뒤의 모든 일정이 달라진다. 이것이 모호하면 "끝났다"는 말이 사람마다 다른 뜻이 된다.

### 크기 문제

**너무 크게 잡으면** 진행 중인 상태가 길어져서 실제로 어디까지 됐는지 알 수 없다. 한 달짜리 Activity가 "50% 진행"이라고 할 때 그 50%가 무엇인지 설명하기 어렵다.

**너무 잘게 쪼개면** 관리해야 할 것이 수천 개가 되어 실제로 갱신되지 않는다. 갱신되지 않는 공정표는 없는 것과 같다.

---

## ④ 선후관계

### 기본 개념

**선후관계(Logic)** 는 작업들 사이의 순서 제약이다.

```text
선행작업 완료  →  착수조건 충족  →  후속작업 시작
```

여기서 핵심은, **순서가 있다는 것과 착수조건이 충족된다는 것이 같은 말이 아니라는 점**이다. 선행작업이 끝나도 자재가 없거나 승인이 안 나면 후속작업은 시작하지 못한다. 그 부분은 ⑥ Constraint에서 다룬다.

### 관계의 종류

| 표기 | 뜻 | 예 |
|---|---|---|
| **FS** (Finish to Start) | 앞이 끝나야 뒤가 시작 | 거푸집 해체가 끝나야 되메우기 시작 |
| **SS** (Start to Start) | 앞이 시작해야 뒤가 시작 | 굴착이 시작되면 일정 간격 두고 흙막이 지보 설치 시작 |
| **FF** (Finish to Finish) | 앞이 끝나야 뒤가 끝남 | |
| **SF** (Start to Finish) | 드물게 쓰인다 | |

실무에서는 FS가 대부분이고 SS가 그다음이다. SS와 FF에는 보통 **Lag(시차)** 가 붙는다. "굴착 시작 3일 후 지보 시작" 같은 식이다.

### 왜 이것이 중요한가

선후관계가 연결되어야 **하나가 밀렸을 때 무엇이 따라 밀리는지** 계산할 수 있다. 연결이 없는 공정표는 날짜 목록일 뿐이고, 지연의 영향을 전혀 알려주지 못한다.

---

## ⑤ Duration

### 기본식

**Duration(기간)** 은 그 작업을 수행하는 데 걸리는 시간이다.

```text
Duration  =  작업량 ÷ 생산성
```

생산성은 보통 "단위 시간당, 1개 조(Crew)가 처리하는 양"으로 표현한다. 예를 들어 하루에 한 조가 20톤을 배근한다면, 100톤은 5일이다.

### 그러나 실제 Duration은 이것만으로 정해지지 않는다

위 식은 **작업 자체에 걸리는 시간**이다. 현장의 실제 기간은 여기에 여러 가지가 더해진다.

| 영향 요소 | 어떻게 작용하는가 |
|---|---|
| **Crew 수** | 조를 늘리면 줄어든다. 단, 작업면이 좁으면 늘려도 안 줄어든다 |
| **작업시간** | 하루 몇 시간 일하는가. 연장근로 가능 여부 |
| **장비** | 장비 대기 시간, 이동·설치·해체 시간 |
| **작업면** | 여러 조가 동시에 들어갈 수 있는 넓이인가 |
| **접근성** | 자재와 인원이 작업 위치까지 가는 시간 |
| **승인·검측** | 중간에 멈춰서 기다리는 시간 |
| **자재 반입** | 한 번에 다 들어오는가, 나눠 들어오는가 |
| **기상** | 우천 시 못 하는 작업인가 |
| **타 공종 간섭** | 같은 자리를 다른 공종과 나눠 쓰는가 |

그래서 **생산성만 알면 기간이 나온다고 생각하면 안 된다.** 특히 "사람을 두 배 넣으면 기간이 절반"이라는 가정은 대부분의 현장에서 성립하지 않는다. 작업면이 늘지 않으면 사람만 늘어나고 생산성은 오히려 떨어진다.

---

## ⑥ Resource · Constraint

### Resource

각 Activity에 필요한 **인원, 장비, 자재**를 붙인다. 그러면 시간축을 따라 "언제 무엇이 얼마나 필요한가"가 나온다.

여기서 문제가 드러난다. 개별 작업은 각각 가능해 보여도, **같은 날 필요한 자원의 합이 현장이 가진 것을 넘을 수 있다.** 여러 작업이 하나의 크레인을 같은 시간에 요구하는 식이다. 이것을 조정하는 일은 1-3 자원관리에서 다룬다.

### Constraint

**Constraint(제약조건)** 는 그 작업의 착수나 진행에 필요하지만 **아직 충족되지 않은 조건**이다.

선후관계와 다르다. 선후관계는 "앞 작업이 끝나야 한다"이고, Constraint는 "앞 작업과 무관하게 이것이 안 되면 못 한다"이다.

주요 종류:

| 종류 | 예 |
|---|---|
| 설계 | 도면 미확정, 설계 불일치 미해결 |
| 승인 | 시공상세 미승인, 시공계획 미승인 |
| 자재 | 납기 미도래, 반입검사 미완료 |
| 장비 | 중복 배차, 반입 지연 |
| 인원 | 특정 기능인력 부족 |
| 작업면 | 선행공정 미완료, 간섭 미해소 |
| 안전 | 안전조치 미완료, 작업허가 미발급 |
| 품질·검측 | 검측 미실시, 시험결과 대기 |
| 외부기관 | 인허가, 점용·굴착 승인, 지장물 이설 |
| 계약 | 계약상 Milestone, 발주처 지정일 |

**Constraint를 목록으로 관리하는 이유**는, 이것들이 대부분 **남이 해소해 주는 것**이기 때문이다. 내가 열심히 해서 없어지지 않는다. 누구에게 언제까지 요청했고, 언제 회신을 받기로 했고, 실제로 해소됐는지를 따로 추적하지 않으면 착수일에 가서야 알게 된다.

---

## ⑦ Baseline

### Baseline이란 무엇인가

**Baseline(기준계획)** 은 승인되어 **얼려 둔** 계획이다. 이후의 모든 비교는 이것을 기준으로 한다.

### 왜 얼려야 하는가

비교할 기준이 움직이면 차이를 말할 수 없기 때문이다.

계획이 밀릴 때마다 계획을 고쳐 버리면, 공정표는 언제나 "계획대로"가 된다. 실제로는 두 달이 밀렸는데 서류상으로는 아무 문제가 없다. 그러면 지연을 발견할 수도, 원인을 찾을 수도, 책임을 가릴 수도 없다.

그래서 **Baseline은 함부로 바꾸지 않는다.** 바꾸려면 정해진 절차를 거친다. 이 절차와 권한은 프로젝트마다 다르므로 계약문서에서 확인해야 한다.

### 계획과 통제의 경계

```text
       ⑦ Baseline
           │
   계획 ───┼─── 통제
           │
     여기까지가     여기부터는
     "정하는 일"    "재고 고치는 일"
```

---

## ⑧ 실행

계획대로 작업이 수행된다. 이 칸에서 실제로 일어나는 일이 1-1의 시공 Flow다.

---

## ⑨ 실적수집

### 무엇을 모으는가

- **실제 시작일과 완료일**
- **현재 진도** — 어디까지 됐는가
- **잔여 기간** — 남은 것을 끝내는 데 얼마나 걸리는가
- **투입 실적** — 실제로 몇 명이 며칠 들어갔는가
- **중단과 그 사유**

### Data Date

**Data Date(상태일, 기준일)** 는 실적과 잔여계획을 나누는 경계선이다. "언제까지의 실적을 반영했는가"를 나타낸다.

```text
              Data Date
                  │
   ←── 실적 ──────┼────── 잔여 계획 ──→
      (일어난 일)  │      (앞으로 할 일)
```

Data Date가 명시되지 않은 공정표는 해석할 수 없다. 같은 공정표라도 어제까지 반영한 것과 지난주까지 반영한 것은 전혀 다른 문서다.

### 이 칸이 가장 자주 빠진다

계획은 세우는데 실적을 같은 기준으로 재지 않는 경우가 매우 흔하다. 그러면 ⑩ 이후가 전부 성립하지 않는다. **계획만 있고 실적이 없는 관리는 관리가 아니다.**

그리고 실적은 **계획과 같은 단위로** 재야 한다. 계획은 WBS 단위인데 실적은 다른 구획으로 모으면 비교할 수 없다.

---

## ⑩ 계획 대비 비교

Baseline과 현재 상태를 견준다.

- 어느 작업이 얼마나 늦었는가 / 빨랐는가
- 진도가 계획보다 앞서는가 뒤처지는가
- 완료 예정일이 어떻게 바뀌었는가

여기서 나오는 차이가 **Variance(차이)** 다. 차이 자체는 좋고 나쁨이 아니다. 다음 칸에서 그 의미를 따진다.

---

## ⑪ 지연 영향 분석

### 지연이 전부 같은 무게를 갖지는 않는다

여기서 두 개념이 필요하다.

**Float(여유)** — 전체 완료일을 늦추지 않으면서 그 작업이 늦어질 수 있는 여유 시간.

**Critical Path(주공정선, CP)** — Float가 없는 작업들이 이어진 경로. 이 경로 위의 작업이 하루 늦으면 **전체가 하루 늦는다.**

```text
   CP 위의 작업이 1일 지연    →  준공일 1일 지연
   Float 5일인 작업이 3일 지연 →  준공일 변화 없음 (Float만 2일로 줄어듦)
   Float 5일인 작업이 8일 지연 →  Float를 다 쓰고 3일 초과 → 준공일 3일 지연
```

그래서 **"며칠 늦었는가"보다 "어디가 늦었는가"가 중요하다.** 같은 3일 지연도 CP 위에서 생긴 것과 여유가 많은 경로에서 생긴 것은 대응이 완전히 다르다.

Float를 다 쓰면 그 경로도 CP가 된다. 즉 CP는 고정된 것이 아니라 **진행에 따라 바뀐다.**

### 무엇을 분석하는가

- 이 지연이 CP 위인가, Float 안인가
- 후속 작업 중 무엇이 따라 밀리는가
- 계약상 Milestone에 닿는가
- 다른 공종과의 간섭이 새로 생기는가

## ⑫ Recovery

### 만회의 수단은 제한적이다

**Recovery(만회)** 는 밀린 것을 되돌리려는 조치다. 실제로 쓸 수 있는 수단은 몇 가지뿐이고, **각각에 대가가 있다.**

| 수단 | 방법 | 한계와 대가 |
|---|---|---|
| **자원 증가** | 인원·장비를 늘린다 | 작업면이 좁으면 효과가 없다. 원가가 는다 |
| **작업시간 연장** | 연장근로, 야간, 휴일 | 생산성이 떨어지고 안전 위험이 는다. 원가가 는다 |
| **병행 수행** | 순차로 하던 것을 겹친다 | 재작업 위험이 커진다. 간섭이 생긴다 |
| **순서 변경** | 논리를 바꾼다 | 기술적으로 가능한지 검토해야 한다 |
| **공법 변경** | 다른 방법으로 바꾼다 | 설계변경·승인이 필요할 수 있다 |
| **범위 조정** | 일부를 뒤로 미룬다 | 계약 범위 문제. 발주처 협의 필요 |

여기서 반드시 기억할 것. **인원을 두 배 넣는다고 기간이 절반이 되지 않는다.** 작업면, 장비, 자재 공급, 검측 능력이 함께 늘지 않으면 추가 인원은 대기한다. 그리고 원가는 확실히 늘어난다.

또한 Recovery 판단은 공정만으로 할 수 없다. **원가(1-4)와 자원(1-3)을 함께 봐야** 한다. 그래서 세 Flow가 이 지점에서 만난다.

## ⑬ Update

### Update와 Revision

두 가지를 구분해야 한다.

| | 뜻 | Baseline |
|---|---|---|
| **Update(갱신)** | 실적을 반영하고 잔여계획을 다시 계산한다 | 그대로 둔다 |
| **Revision(개정)** | 계획 자체를 다시 만든다 | 새로 정한다 |

일상적으로 하는 것은 Update다. Baseline은 그대로 두고, Data Date를 옮기면서 실적과 잔여를 갱신한다. 그래야 Baseline과 비교가 계속 가능하다.

Revision은 계획이 더 이상 의미가 없을 정도로 조건이 바뀌었을 때만 한다. 설계변경으로 범위가 크게 달라졌거나, 계약기간이 조정된 경우다. **Revision의 절차와 승인 권한은 계약문서가 정한다.**

그리고 갱신된 계획으로 다시 ⑧ 실행으로 돌아간다.

---

## 되돌아가는 지점

```text
 ①  ②  ③  ④  ⑤  ⑥  ⑦  →  ⑧  ⑨  ⑩  ⑪  ⑫  ⑬
                             ↑              │
                             └──────────────┘
                              통제 고리 (상시)

 ①~⑦ 로 되돌아가는 경우 = 범위나 조건 자체가 바뀌었을 때 (Revision)
```

평소에는 ⑧~⑬이 계속 돈다. 주기는 현장마다 다르지만 보통 주 단위 또는 월 단위다.

계획 구간으로 되돌아가는 것은 예외적인 일이다. 설계변경으로 물량이 바뀌면 ⑤ Duration부터 다시 봐야 하고, 범위가 바뀌면 ② WBS부터 다시 봐야 한다. 이 연쇄는 1-8에서 다룬다.

---

## 자주 혼동하는 개념

| | | 차이 |
|---|---|---|
| WBS | Activity | 전자는 결과물(무엇), 후자는 작업(어떻게 하는 일). 전자에 순서가 들어가면 안 된다 |
| 선후관계 | Constraint | 전자는 작업 간 순서, 후자는 작업 외부의 미충족 조건 |
| Baseline | 현재 공정표 | 전자는 얼려 둔 기준, 후자는 실적이 반영된 현재 상태 |
| Update | Revision | 전자는 Baseline 유지, 후자는 Baseline 변경 |
| 지연 | CP 지연 | Float 안의 지연은 준공일에 영향이 없다 |
| Duration | 작업량÷생산성 | 후자는 전자의 일부일 뿐이다 |

## 잘못 이해하면 생기는 일

**②③④를 건너뛰고 날짜부터 잡으면** — 왜 그 날짜인지 설명할 수 없고, 하루 밀렸을 때 무엇이 영향받는지 계산할 수 없다. 공정표가 날짜 목록이 된다.

**Activity 완료조건을 정하지 않으면** — "끝났다"의 뜻이 사람마다 달라진다. 배근을 끝낸 것인지 검측을 통과한 것인지 모른 채 후속 일정을 잡는다.

**선후관계를 연결하지 않으면** — 지연의 파급을 전혀 알 수 없다. 개별 작업이 늦은 것은 보이는데 준공일에 무슨 일이 생기는지는 모른다.

**Constraint를 관리하지 않으면** — 착수 당일에 도면이 없거나 자재가 없다는 것을 발견한다. 그때는 이미 늦다.

**Baseline을 계속 고치면** — 언제나 "계획대로"인 공정표가 된다. 지연이 서류에서 사라진다.

**실적을 안 모으면** — ⑩ 이후 전부가 성립하지 않는다. 비교할 실제가 없다.

**Float를 보지 않고 지연에 반응하면** — 여유가 많은 곳에 자원을 쏟아붓고, 정작 CP 위의 작업은 방치한다.

**인원을 늘리면 기간이 준다고 가정하면** — 원가만 늘고 기간은 그대로인 조치를 한다.

## 스스로 확인

1. 계획 구간과 통제 구간의 경계는 어느 칸인가. 왜 그 자리인가.
2. WBS에 순서를 넣으면 안 되는 이유는 무엇인가.
3. 선후관계와 Constraint는 어떻게 다른가. 각각 누가 해소하는가.
4. Duration을 "작업량 ÷ 생산성"으로만 잡으면 무엇이 빠지는가. 다섯 가지를 들어 보라.
5. Baseline을 얼려 두는 이유는 무엇인가. 고치면 무엇을 잃는가.
6. Data Date가 없는 공정표를 해석할 수 없는 이유는 무엇인가.
7. 같은 3일 지연인데 대응이 달라지는 경우는 어떤 경우인가.
8. Recovery 수단 여섯 가지와 각각의 대가를 말해 보라.
9. Update와 Revision은 무엇이 다른가.
