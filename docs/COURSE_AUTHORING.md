## 1. 이 교재가 무엇인가

롯데건설 토목 IM 담당자용 실무 학습 교재다. 정적 웹사이트로 배포된다.

### 최우선 원칙

```text
챕터 1 — 기본 Flow      "골격"    현장이 어떤 논리로 돌아가는가
      ↓
챕터 2 — 올바른 상황    "정상"    공종별로 정상적인 순서는 무엇인가
      ↓
챕터 3 — 문제풀이       "이상"    어긋났을 때 어디로 돌아가고 무엇을 확인하는가
```

> **상황을 통해 개념을 처음 배우게 하지 않는다.**

이것이 이 교재를 다시 설계한 이유다. 이전 구조(`docs/a01`)는 개념과 상황이 한 파일에 섞여 있어서, 학습자가 "왜 이 질문을 해야 하는가"가 아니라 "이 사례에서는 이 질문을 했다"를 외우게 됐다.

최종 목표는 사례를 많이 아는 사람이 아니라 **새로운 현장 상황을 기존 개념체계에 끼워 넣어 해석할 수 있는 사람**을 만드는 것이다.

### 세 개의 축

섞으면 안 된다.

| 축 | 내용 | 어디에 |
|---|---|---|
| 관리업무 | 공정, 자원, 원가, 품질, 문제처리 | 챕터 1 |
| 공종 | 토공, 가시설, 철근, 거푸집, 콘크리트, 터널 | 챕터 2 |
| 직무 | 공사, 공무, 품질, 안전 | 1-9, 챕터 3 |

세 축은 **챕터 3에서만 만난다.**

## 4. 작성 규칙

### 챕터 1 (개념층) — 이미 완료됐지만 수정할 일이 있다면

- **특정 날짜·인물·현장이 등장하면 안 된다.** `tools/validate.js`가 차단한다
- 용어는 나오는 자리에서 정의하고 **왜 필요한지**까지 쓴다. 한 줄 정의로 끝내지 않는다
- 도식 예시(무명의 BOX 구조물 트리 등)는 허용

### 챕터 2 — 공통 서식

```text
① Flow 도식             정상 순서
② 왜 이 순서인가         각 칸이 앞뒤로 바뀌면 무슨 일이 생기는가
③ Hold Point           되돌릴 수 없는 지점은 어디인가
④ 정상 판정 기준         무엇이 확인되면 제대로 된 것인가
⑤ 다음 공종에 넘기는 것   인계 대상과 증빙
⑥ 이상의 신호와 그 의미   무엇이 보이면 무엇을 의심하는가
```

`⑥`이 챕터 3으로 이어지는 다리다. **표로 만들고 12줄 안팎**을 목표로 한다. 이 표가 부실하면 케이스가 풀리지 않는다.

각 절은 **300줄 안팎**. 끝에 `## 스스로 확인` 질문 10개 내외.

### 챕터 3 — 공통 서식

```text
① 상황              정보가 일부 비어 있다
② 제공된 자료        표. "확인 필요"를 일부러 남긴다
③ 먼저 답해볼 것      읽자마자 스스로 답하게. 4문항
④ 무엇이 깨졌는가     어느 Flow의 어느 칸인가
⑤ 공사 담당자라면     지금 당장 할 일
⑥ 공무 담당자라면     오늘 안에 남길 것
⑦ 합의해야 할 것      두 직무가 반드시 맞춰야 하는 것
⑧ 부족한 정보        무엇을 더 알아야 판단이 끝나는가
⑨ 흔한 오답          왜 틀렸는가. 6~7개
```

**④~⑨는 `<details>` 블록 안에 넣는다.** 학습자가 먼저 답하고 펼치도록. 열고 닫는 태그 개수가 맞아야 한다(각 6개).

`<details><summary>펼치기</summary>` 는 **한 줄에** 써야 렌더러가 인식한다. `</details>` 는 단독 줄.

각 케이스는 **200줄 안팎.** 끝에 `## 이 문제가 가르치는 것` 으로 한 문장 교훈을 남긴다.

### 케이스 설계에서 가장 중요한 것

> **케이스마다 실패의 종류를 다르게 잡는다.**

같은 공종의 케이스 5개가 전부 "확인하고 조치한다"면 하나만 있어도 된다. 지금까지 쓴 10개는 이렇게 갈라 놨다.

| 케이스 | 가르치는 실패 유형 |
|---|---|
| 3-01 | 신호의 해석 (탁도 = 흙) |
| 3-02 | 원인 후보가 여럿일 때 |
| 3-03 | 현장 안이 멀쩡한 게 안전의 증거가 아니다 |
| 3-04 | 투입과 성과의 혼동 (주입량 ≠ 차수) |
| 3-05 | 원가가 안전 판단의 입력이 되는 것 |
| 3-06 | 아무도 잘못하지 않은 문제 (계약으로 처리) |
| 3-07 | 평균이 원인을 가린다 |
| 3-08 | 순서에 예외가 없는 경우 (대피 > 기록) |
| 3-09 | Hold Point를 지나친 대가 |
| 3-10 | 통제할 수 없는 Constraint |

**새 케이스를 쓸 때 이 표를 보고 겹치지 않는 유형을 고른다.** 아직 안 쓴 유형 예시: 여러 사람이 각자 옳은 말을 해서 결정이 안 나는 상황 / 이미 늦은 것을 뒤늦게 발견한 상황 / 지시가 상충하는 상황 / 협력업체와 이해가 갈리는 상황.

### 챕터 1을 계속 회수한다

케이스마다 챕터 1의 어느 절로 돌아가는지 **명시적으로 인용한다.** `(1-5 ②)`, `(1-10 ③)` 같은 식으로. 이것이 3챕터를 하나로 묶는다.

## 5. 반드시 지킬 것

1. **일반원칙과 프로젝트 고유절차를 구분한다.** 검측 명칭, 승인 권한, 통지 기한, 문서 양식은 계약조건과 조직체계가 정한다. **지어내지 않는다.** "프로젝트 문서에서 확인한다"고 쓴다
2. **수치는 교육용 가정임을 명시한다.** 각 케이스 머리에 표기
3. **기존 자료를 건드리지 않는다.** `docs/a01`, `docs/a02`, `docs/part_a`, `docs/part_b`, `docs/field` 는 보존
4. **개념과 CASE를 한 파일에 섞지 않는다**

## 6. 빌드와 검증

새 `.md` 를 쓴 뒤 반드시 실행한다.

```sh
node tools/build-course.js      # docs/ch*/ → data/course.js
node tools/course-render-qa.js  # 브라우저 없이 렌더링 검증
node --check app.js
```

`course-render-qa.js` 는 절 개수를 데이터에서 읽으므로 **묶음이 늘어도 고칠 필요 없다.**

### 링크 검사

`tools/validate.js` 가 전체 검증을 하지만, **`docs/field/tasks/A01.md → ../cases/F02.md` 가 깨져 있어 항상 실패한다.** 이것은 이 작업 이전부터 있던 문제다(`git stash` 로 확인함). 교재 부분만 따로 확인하려면:

```sh
node -e "
const fs=require('fs'),path=require('path');
function walk(d){return fs.readdirSync(d,{withFileTypes:true}).flatMap(e=>e.isDirectory()?walk(path.join(d,e.name)):e.name.endsWith('.md')?[path.join(d,e.name)]:[]);}
let bad=0;
for(const f of [...walk('docs/ch1-flow'),...walk('docs/ch2-normal'),...walk('docs/ch3-problem'),'docs/CURRICULUM_STRUCTURE.md']){
  for(const m of fs.readFileSync(f,'utf8').matchAll(/\[[^\]]+\]\(([^)]+)\)/g)){
    if(/^(https?:|#)/.test(m[1]))continue;
    if(!fs.existsSync(path.resolve(path.dirname(f),decodeURIComponent(m[1].split('#')[0])))){console.log('BROKEN',f,m[1]);bad++;}
  }
}
console.log(bad?bad+' broken':'links ok');"
```

### 목차 갱신을 잊지 않는다

새 절을 쓰면 세 곳을 고친다.

- `docs/ch2-normal/README.md` 또는 `docs/ch3-problem/README.md` — *(작성 예정)* 을 링크로
- `docs/CURRICULUM_STRUCTURE.md` — 목록과 「작성 현황」 표

## 8. 함정 목록

작업 중 실제로 걸렸던 것들이다.

| 함정 | 내용 |
|---|---|
| **빈 디렉터리** | git은 빈 디렉터리를 추적하지 않는다. `git stash -u` 하면 사라진다. `mkdir -p` 로 다시 만들면 된다 |
| **`.golden-entry` 개수** | `tools/a01-web-qa.cjs` 가 1개로 단언한다. 교재 카드는 `.course-entry` 로 분리해 뒀다. 새 진입 카드를 만들 때 `golden-entry` 를 쓰지 않는다 |
| **셸 백틱** | `node -e "..."` 안에 백틱을 쓰면 zsh가 명령치환한다. 긴 스크립트는 `node <<'JSEOF'` heredoc 을 쓴다 |
| **크로스-realm 배열** | `vm` 컨텍스트에서 꺼낸 배열은 `assert.deepEqual` 이 프로토타입에서 실패한다. `.join(',')` 으로 비교한다 |
| **문서 끝 네비게이션** | `build-course.js` 가 파일 마지막의 "목차" 링크 줄을 잘라낸다. 웹에는 안 나온다. **본문에 필요한 내용을 마지막 줄에 두지 않는다** |
| **예시 속 링크 표기** | 설명문에 대괄호와 괄호를 붙여 쓰면 링크 검사기가 실제 경로로 읽고 깨졌다고 본다. 코드 표기로도 안 걸러지니 표현 자체를 바꾼다 |
| **`<details>` 균형** | 열고 닫는 개수가 맞는지 `grep -c` 로 확인한다 |

## 10. 품질 기준

절이나 케이스를 다 쓴 뒤 스스로 점검한다.

### 챕터 2

- 실제 상황 없이도 순서가 이해되는가
- Flow의 각 칸에 "무엇이 끝나야 다음으로 가는가"가 있는가
- Hold Point가 **왜 거기인지** 설명되어 있는가 (대개 비가역성 때문이다)
- 「이상의 신호」 표가 챕터 3 케이스를 풀 수 있을 만큼 구체적인가
- General Rule과 프로젝트 고유절차가 구분되어 있는가

### 챕터 3

- 챕터 1과 2에서 배운 것만으로 풀 수 있는가. 안 배운 지식을 갑자기 요구하지 않는가
- 정보가 **의도적으로** 비어 있는가. `⑧ 부족한 정보` 와 짝이 맞는가
- 공사와 공무의 답이 실제로 다른가. 같으면 직무를 나눈 의미가 없다
- 다른 케이스와 **실패 유형이 겹치지 않는가**
- 챕터 1의 어느 절로 돌아가는지 인용되어 있는가
